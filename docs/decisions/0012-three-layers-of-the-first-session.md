# 0012 — The three layers of a repository, generated in its first session

- Status: accepted; amends [0006](0006-context-at-the-right-moment.md) (MAP.md is apart from AGENTS.md again) and [0003](0003-what-stays-and-what-goes.md) (action budget 37 → 44)
- Date: 2026-10-29
- Decided by: the implementing agent, within the maintainer's brief (phase I: baseline, OKF memory and a compact verification layer, generated in the first session, not filled in by hand)

## Context

After bootstrap a repository had an `AGENTS.md` full of `(placeholders)` with a table of paths, an empty memory and a test command typed by hand (`npm test` by default, whatever the project was). The human was expected to fill all of it. Meanwhile every check an agent ran poured its whole output into the agent's context.

The evidence about generated context is not in favour of "let an LLM write it": context files generated by an LLM that restate what the agent can discover lower the success rate slightly and raise cost by 20–23 % ([arXiv:2602.11988](https://arxiv.org/abs/2602.11988)); a compressed index in `AGENTS.md` beat skills that were not invoked ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). Human-written files help mostly where practice is non-standard.

## Decision

Generated content is limited to three kinds; everything else stays out.

1. **Deterministic, no LLM.** `MAP.md` (a file apart from `AGENTS.md`, which links to it) is derived from the repository: stack and commands from manifests, CI, Makefile, tox/nox and pre-commit (Node/TS, Python, Rust, Go, Java; an unknown stack gets the layout only), top-level folders and their children, entry points, test layout, ignored and CI files. Folder purposes, which cannot be derived, live in `.ways/map-notes.json` (path → one line) and are merged in. `ways map` regenerates it; `ways map --check` fails on drift, judged by a fingerprint in a marker line (top-level folders, stack, commands, entry points, CI, notes) so that adding a file does not count. The brief and `ways status` mention drift; nothing blocks.
2. **Facts the code does not say.** The `onboarder` (a sixth-line role like the reviewer and the documentalist) reads history, CI, comments, ADRs and READMEs and writes 8–15 facts of at most 15 lines, each with `sources`. ways, not the agent, stamps each source's hash and marks the fact `generated: process:ways-onboard` with no `verified`: it is **unverified** until a person runs `ways memory confirm <id>` at a terminal (like `ways approve`, an agent's shell cannot). `ways memory check` refuses a seeded fact without sources or whose sources or `paths` name nothing; onboarding drops such facts (only files it created) and keeps at most 15. A fact whose source changed is marked stale in the brief and the rules, never hidden. Confirmation by use (a `done` touching the area without contradicting it) is **not** implemented: "did not contradict" cannot be told apart from "did not look" without judgement ways does not have.
3. **Check commands validated by running them.** A command becomes a check only after ways ran it: cannot start, exit 126/127, a missing script or module, "no tests ran", or a failure no known tool reported → rejected with the reason. One that runs is kept with its line base (passing, or the failures it already has). Bootstrap does this for every detected candidate (the first that works per check wins, so `python -m pytest` and `python3 -m pytest` can both be tried); the onboarder can only *propose* commands in `.ways/checks.json` `proposed`; `ways check add <name> -- <command>` does it by hand.

`AGENTS.md` stays under 100 lines: bootstrap writes it once with what was detected and validated (`npx ways run test` (runs `npm test`)), the link to `MAP.md` and five lines on ways, and no placeholders. The onboarder proposes additions in `.ways/agents-proposal.md`; ways moves them into one marked block (`<!-- ways:onboarder:start -->`), replacing only that block, so the human sees them in the diff and their own text is never rewritten.

**The verification layer is `ways run`.** It runs the real configured command and returns a summary instead of the output: status, duration, counts, each failure on one line with its first error lines (parsers for vitest, jest, pytest, cargo, go, tsc, eslint, ruff and mypy; a generic reading otherwise, and when a parser throws or finds nothing on a failed run), at most 40 lines and 2,000 characters (`.ways/checks.json` `output`), one line when everything passes, and the whole log in `<git-common-dir>/ways/runs/<id>.log` (`ways run --show <id> --grep=… --tail=…`). The exit code is the check's. Failures are split into **new** and **already failing at the base**: the base is the active work's base, or HEAD when the tree has changes; it is compared with the newest *clean* run of the same command on that commit, else with the line base in `.ways/checks.json` (which a fresh clone and CI have). `ways check`, `ways done` and `ways verify` go through the same wrapper, so the evidence of every check and verifier keeps the summary, the run id and the log path besides the command, exit code, duration and sha256. `ways check` prints one line per area. It is not a benchmark of the agent: no history replicas, no `evals run --project`.

**Where the commands live.** The contract stays `commands` in `.ways/config.json`, on the verifier surface, so changing a check still needs the human. `.ways/checks.json` holds observations that decide no verdict (source, duration, `slow`, line base, proposals); it is not on the surface. Adding a check to an existing contract (every earlier command unchanged, the required list only grown) is free, like adding a test; changing or removing one is not.

**First session.** Bootstrap leaves `.ways/onboarding.json` `pending`. The SessionStart hook (and UserPromptSubmit while it is pending, once per session) injects a notice of at most 600 characters: what onboarding generates, which agent, how many files it may read, that it spends the human's quota, and the command. Config `onboarding: ask | auto | off`, `ask` by default: `ways onboard` starts an agent only with `--yes` or a yes at the terminal; without one it says how to ask (`ways ask`) and exits 2. ways never starts an LLM silently. Without an agent it does the deterministic part and says what is missing; `--refresh` updates stale facts; it is idempotent (existing notes and facts are kept and listed in the brief so they are not duplicated). The onboarder runs as a new process with only its paths writable (tools it is started with, the guard and the commit hook by `WAYS_ROLE=onboarder`, then a comparison of the tree: anything else, or a commit, fails the run and nothing is marked done), and its session is on the event bus with its role.

**Using `ways run` without being led.** `AGENTS.md` lists the checks as `npx ways run <check>`. When the agent runs one of the configured commands by hand (`pytest`, `npm test`, `eslint .`), ways suggests `ways run <check>` once per session, in one line, and never blocks: in Claude Code from PreToolUse (`additionalContext`, filtered by `if` rules for the common runners), in pi appended to the tool result, since pi's `tool_call` cannot add context.

## Consequences

- CLI: 44 actions (was 37): `run`, `run --show`, `check add`, `map`, `map --check`, `onboard`, `memory confirm`. Bootstrap writes 28 files by default (was 23): `MAP.md`, `.ways/checks.json`, `.ways/onboarding.json` and the onboarder for Claude Code and pi.
- Bootstrap without `--test-command` now runs the detected checks once each (bounded at 5 minutes per command; one that runs longer is kept as `slow` with an unknown line base). A repository where nothing runs gets a test check that fails with how to add one, so `ways done` cannot pass on nothing.
- On the development host the summaries of synthetic runs of 6,000+ lines were 0.1–0.2 % of the raw output (≈390,000 → 300–500 characters; `tests/run-parsers.test.ts` prints the numbers). The fixtures for jest, pytest, cargo, go, tsc, eslint, ruff and mypy are written to the tools' output formats, not recorded from real runs (only Node is installed here); a format the parsers do not know falls back to the generic reading, never to silence.
- The MAP drift check on the hook path runs `git ls-files` and the detection once per HEAD and index change (cached); the first hook after a commit pays it.
- `ways check` reports integrity by area (harness files, config, agents, memory) and every check through `ways run`'s summary; work records, trailers and the verifier surface stay with `ways check --history` and `ways done`, which the report says in one line, rather than adding a slower history audit to every local run.
- `ways run <check> -- <args>` runs a narrower command (one test file); it is compared only with earlier runs of that same command.
- The package moves to `0.3.0-dev.1` so `ways upgrade` can tell a 0.3.0-dev.0 repository apart.
- The Claude Code flags for the onboarder (`--allowedTools` with path patterns, `--settings` with the guard) and PreToolUse `additionalContext` follow the documentation read for 0006 and 0009 and were exercised only with fake agents.
