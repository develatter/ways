# 0008 — Control plane: a derived board and an inbox in files

- Status: accepted
- Date: 2026-10-29
- Decided by: the implementing agent, within the maintainer's brief (a kanban of what each agent does, in the spirit of Symphony but without a dispatcher; an inbox where the orchestrating agent puts what it expects from the human; useful on day one; zero new dependencies; minimal ceremony)

## Context

The hooks (0006) already log every agent event to a JSONL bus in the Git common directory, and the records and runs say where each work stands. What was missing: one place where the human sees every agent at once, and a channel for "the agent needs something from me" and "I need to tell that agent something" that does not depend on the human being in that agent's terminal. The analysis (§5, F5) proposed a board, SSE and an inbox; Agent Deck and Agent Orchestrator show that files and hooks are enough.

## Decision

1. **The board is a projection.** Cards are computed on every refresh from `git worktree list`, each worktree's *own* active pointer and its records, the last `ways done`, the event bus (followed incrementally: each refresh reads only appended bytes) and the inbox. Nothing is dragged and nothing is stored for the board. Columns by precedence: Done (closed in 7 days) → Waiting for you (open inbox item, `ways block`, pending approval) → Blocked (stalled 10 min without a hook event, or the last `ways done` failed and no agent is on it) → Verifying (review pending) → Working → Preparing (no commits yet, or an agent with no work). An agent whose turn ended on an open work is *waiting for you*: that is what the human must act on. Reasons travel as codes so the page translates them.
2. **The inbox is files**, `<git-common-dir>/ways/inbox/<id>.json`, out of history: it is operational conversation. Types `ask`, `decision` (options and a default that applies at expiry, so nobody waits forever), `approval`, `block`, `instruction`; states `open → answered → delivered → closed`, plus `expired`; each item keeps its history. *Deviation from the analysis:* `instruction` goes from the human to an agent, as the brief asks (the analysis had it as a manual task for the human; that is an `ask` with options).
3. **Delivery once, by the hooks.** SessionStart and UserPromptSubmit inject answers and instructions as context; Stop keeps the agent going with them (even when a stop hook already did: each item is said once, so it cannot loop). "Once" is enforced by an exclusive create of `.claims/<id>`, not by the session state, so two hooks or `ways ask --wait` never deliver the same answer twice. Routing: to the asking session; a *new* session in the same worktree also takes what its predecessor never got (Claude Code changes the session id on `/clear`). SessionStart writes `WAYS_SESSION` into Claude Code's `CLAUDE_ENV_FILE` (only a plain id: it is a shell file), and the pi extension sets it, so `ways ask` knows who asks; without it the worktree routes. Not PostToolUse: Claude Code runs it asynchronously, and an answer marked delivered must have reached the model.
4. **CLI for agents and orchestrators, `--json` everywhere**: `ways ask [--wait]` (exit 0 answered, 2 still open, 3 expired or closed; Agent Deck's convention), `ways inbox [list] | show | answer | close | tell`. `ways block` also creates a `block` item; a passing `ways done` or `ways cancel` closes it. A `ways-orchestrator` skill states the protocol in two lines.
5. **Approvals stay derived.** A work's pending approval is not copied into the inbox; the board derives it from the record. Answering it calls `approveFromBoard`, which approves exactly the work and evaluated commit the page showed and records `via: "board"`. Where the base requires SSH-signed approvals the board refuses and shows the exact `ways approve --key=…` command: a page cannot sign. `ways inbox answer` never approves a work.
6. **`ways serve` with `node:http` only.** Bound to 127.0.0.1. A 256-bit token (constant-time comparison) from the printed URL (GET only), `Authorization: Bearer`, `X-Ways-Token` or an `HttpOnly; SameSite=Strict` cookie named per port. `Host` must be a loopback name with the server's port (DNS rebinding); a foreign `Origin` or a cross-site `Sec-Fetch-Site` is refused; no CORS at all; mutations need a JSON body (so no form can post cross-origin) of at most 16 KiB. CSP by hash of the page's single inline script and style. `serve.json` is written 0600 and removed on exit. SSE pushes a new state when its hash changes, triggered by `fs.watch` on the events and inbox directories and a 1 s poll (worktrees, HEADs, records).
7. **One static page** (`assets/ui/index.html`, about 26 KB): vanilla JS and CSS inline, text only through text nodes, system fonts, light/dark, keyboard-usable, en/es dictionaries in the page (language from `--lang`, `~/.config/ways/config.json` or the page's toggle). *Deviation from the analysis:* not TypeScript compiled into `assets/ui/` modules: one file with no build step is smaller to ship and to audit, and the derivation it would type lives on the server.
8. **Several repositories** through `~/.config/ways/registry.json`; each `ways serve` adds the repository it runs in, `--repo` adds others. `--demo` runs made-up data through the same derivation.
9. **Action budget 28 → 33**: `serve`, `ask`, and the inbox's list (with show), answer, close and tell. The control plane is a new capability, not ceremony on the delivery path: an agent that never asks anything sees no new command.

Not done (as the brief says): a dispatcher, MCP, A2A, OTLP, SQLite, remote access, dragging cards, storing prompts. Inbox transitions are not mirrored into the event bus: the item's own history is the trail, and the board watches the inbox directory directly.

## Consequences

- The human answers from the board, from `ways inbox`, or not at all (decisions with a default resolve themselves at expiry).
- **Honest limit:** the token keeps browsers and other sites out, not the user's own agents, which run as the same user and can read `serve.json`. An unsigned approval from the board is exactly as strong as one from a terminal (an agent can fake a TTY); repositories that need the guarantee set `approvals.signature: required`, and then only a signature counts, wherever it is made.
- Liveness comes from hook events. Claude Code's PreToolUse/PostToolUse hooks are installed only for the tools ways guards or that write files, so a long `Bash` run shows as "no hook event for N min" after 10 minutes. Installing a PostToolUse hook on every tool would fix it at the cost of one Node start per tool call; not done.
- An agent learns of an answer at its next prompt, stop or session start. An idle agent (turn ended) gets it only when the human prompts it; `ways ask --wait` is the synchronous path.
