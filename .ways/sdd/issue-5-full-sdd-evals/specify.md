# specify

Goal: Specify the D harness, observable metrics, validity and the comparison report.
Evidence: Issue #5 acceptance criteria and the explore findings.
Decision:
1. `--harness=full-sdd` is accepted beside `no-ways` and `checks-only`. For it, after the fixture commit the runner bootstraps the running Ways package into the disposable repo with the task's regression checks as the test command, links `node_modules/@develatter/ways` and `node_modules/.bin/ways` (ignored by Git), and commits the bootstrap before any session. The adapter receives `WAYS_EVAL_WAYS_BIN`, and the prompt is prefixed with a recorded harness instruction to deliver through `npx ways sdd start <task-id>` without bypassing gates, reviews or checks. A/B repos are unchanged.
2. Results bump to `schemaVersion: 2` and record `waysRevision` (`packageVersion`, `harnessVersion`, `sourceRevision` or null with reason, `contentDigest` over `dist/` and `assets/`) for every run, plus `evidence.kind` = `fixture` for the fake adapter or programmatic adapters flagged synthetic, else `real`.
3. Per task, `compliance` is `{applicable:false, reason}` for A/B. For D it is graded from the repo after the last session: history-audit and integrity issues, SDD works started/closed, downgrades, remediation attempts, validation failures, whether an SDD work is still active, `compliant` (no issues and no active work) and `fullSddCompleted` (compliant and at least one close certification). Task success stays the independent functional grade and never depends on compliance.
4. Per task `metrics` hold `{value, source, reason?}` entries: adapter-reported `toolCalls`, `contextCompactions`, `retries`, `humanInterventions`, `stalls` (null with reason when not reported); runner-observed `timeouts` and `resumeSuccess` (null with reason for tasks without resume); repository-observed `remediationAttempts` (null with reason outside D). Adapter JSON may carry `metrics` with non-negative integers or null; invalid values make the session error. Token/cost usage keeps the #4 semantics.
5. `ways evals compare --input=<file>... [--output=<json>] [--markdown=<md>]` reads raw results, digests each file, marks unparseable or non-v2 files `invalid`, and marks runs `non-comparable` when corpus id/revision, model, seed, budgets or adapter argv differ from the reference (first valid real run, else first valid run) or when fixture and real evidence are mixed. Only comparable runs are scored per harness: task success rate, regressions, incorrect done claims, compliance rate (D only), metric totals with counts of available/unavailable values. Every score lists its source artifacts (path, sha256, runId). The report states `architecturalClaim:false` and separates `taskSuccess` from `harnessCompliance`. The exit code is 0 when at least one comparable run exists.
Gate: Specification complete and testable with deterministic fixture adapters, including a programmatic adapter that drives a real SDD lifecycle in the disposable repo.
